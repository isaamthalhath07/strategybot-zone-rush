# Offline team compute

The worker executes the actual pinned Python bot and its original opponents on
the CPU. It does not use CUDA for policy decisions. A returned game is pending
owner acceptance; a progress counter never creates campaign credit.

The architecture-control coordinator is `distributed_campaign.control`. It
separates these jobs:

1. The owner freezes the four-source study before observing any study outcome.
2. `qualification prepare-control` creates the eight preregistered original
   study cases and audits them with the original all-actor/two-referee auditor.
   The study directory owns their authenticated canonical log. Packaging those
   same cases again executes zero new games.
3. Each helper executes eight full qualification replicas and full audits on
   its existing CPython 3.12 release. The owner authenticates exact recorded
   behavior and issues an approval for that exact runtime and source scope.
   Replicas receive no study or primary credit. A structural architecture needs
   explicit source coverage; numeric CONFIG qualification does not cover it.
4. `control prepare` freezes actual remaining PLAY assignments. Helpers return
   authenticated, resumable complete game records. `control ingest-play` checks
   their physical transcripts and preserves the exact authenticated creator.
   A study-owned authenticated reservation fixes one canonical controller
   output before any assignment is issued. A second output/registry cannot
   start another original-game cohort; acceptance also has a study-owned seal.
5. `control prepare-audits` freezes original-row audit jobs for a different
   registered physical helper. This includes the eight original owner gold
   rows. Qualification replicas are never relabeled as these original audits.
6. The auditor uses the unchanged original auditor to regenerate all 320 actor
   callbacks and check both referees. `control ingest-audit` authenticates the
   proof against its exact original row, creator, source and runtime.
7. `control finalize` rechecks complete identities, every physical transcript,
   actual peer signatures and source-specific proof coverage. The owner also
   regenerates predeclared canaries covering each focal source/helper cohort.
   Acceptance describes the full replay as remote-origin and canaries as owner
   work. It credits extra controls only, with no policy deployment.

The old `owner` primary controller remains a separate prototype with full owner
audit on finalization. It must not be presented as the new remote-audit primary
admission path. The reviewed architecture study does not silently modify the
existing primary catalog or its first 100,000 admitted games.

## Credentials and trust

An owner-only registry supplies a different private key for each helper, plus a
separate owner authorization key. Keys stay in ignored private configuration;
they are never in packages, actor jobs, returned results or Git. Spawned actor
processes receive public job/source data and no credential objects.

HMAC authenticates a cooperative team credential and the owner-issued immutable
assignment. It does not prove computation, host integrity or physical machine
independence. The owner must assign physical identities from the actual team
inventory. Two logical test credentials on one laptop validate protocol rules,
and do not demonstrate actual cross-laptop computation. A compromised helper or
colluding pair is outside this trust model. Owner canaries provide additional
checks, rather than replacing full peer coverage.

An exact repeated result transfer is idempotent. A newly replayed replica with
different timing fields is a different original record and conflicts with an
already imported result. Source drift, incomplete coverage, changed runtime,
same-physical creator/auditor, missing keys and invalid signatures fail closed.
Do not use cross-host timing differences as architecture speed evidence:
assignment and hardware may correlate even when all actions match exactly.

## Running and recovery

Generate credentials and owner approvals before preparing real assignments.
Each generated package contains a command with its published manifest SHA.
Use a short extraction path such as `%USERPROFILE%\ZoneRush`. Put only the
separately delivered credential file in a dedicated private folder and use the
explicit credential-hardening option on first setup. No global Python or CUDA
reinstallation is required for an already qualified CPython 3.12 release.

Run the same worker command to resume. An OS-held lock rejects concurrent writers
to one result folder. The worker preserves an interrupted JSON tail before
truncating it, authenticates committed records, and executes only missing jobs.
It keeps at most twice the worker count in flight and cancels queued work on a
failure. Return only the complete results folder, without private credentials.

Gold computation has a stricter once-only boundary. A committed prefix resumes
the remaining gold cases. A crash after a start marker but before a durable
outcome requires explicit recovery review and is never silently rerun. A
completed witness with a missing row is corruption, not missing work. Partial
gold qualification package creation may be preserved and recreated in a fresh
package output folder, reusing the same canonical witness with zero new game jobs. A separate
OS-held output lock prevents two simultaneous packaging requests in one folder.
The real study controller's original-job output is reserved once. An interrupted
controller-package build needs explicit recovery review at that canonical
output; choosing another output cannot silently create a second study cohort.
If `plan.json` already exists, resume the same request at that output. If it does
not exist, first stop the failed preparation and confirm that no partial ZIP or
assignment was dispatched. Preserve the partial `play` folder and ZIPs in a
clearly named backup inside the reserved output, then retry the exact same
request there. Keep the authenticated study binding and canonical gold intact.
Do not perform that recovery if a helper may already have received those jobs;
preserve all files for an explicit task/provenance reconciliation instead.

These tools are not an automatic campaign starter. Real dispatch and any
versioned primary migration require the owner to review the frozen sources,
runtime qualification and bounded integration evidence first. The finite
qualification/evidence cannot establish universal cross-version equivalence.
