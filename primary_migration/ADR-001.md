# ADR-001: Continue the same two-million-game campaign with a versioned primary protocol

**Status:** Proposed; implementation and execution are not authorized by this document.

**Date:** 2026-11-09

**Deciders:** Campaign owner and independent protocol reviewer. Architecture allocation remains conditional on the completed four-arm study.

## Context and fixed accounting

The existing campaign is `66269bc2443cdff375116b3e168f1e8db6f27cc4a758a8c00e84f949d4bcac10`.
Its immutable catalog SHA is `311b51f5eef35402f88887bd18f54053fedf923cc17d3b8b13d6d1e2142f794f`.
It contains 10,000 distinct map rotation orbits, with the original 8,000/1,000/1,000 training/development/final split. Maps retain their original content, global indices, phase indices, generation seeds and order.

The observed terminal handoff and the owner's latest read-only coverage check identify five admitted stages, `train_000` through `train_004`: 500 maps, 100,000 full matches, 300,000 distinct rival IDs and 300,000 distinct rival seeds. Their original all-actor audits covered 32,000,000 callbacks. The monitor is structural verification of existing receipts, not a new replay of those callbacks. The migration must preserve that distinction.

The 32,768-match four-arm architecture study is EXTRA evidence. Its eight canonical reference matches are consumed study outcomes, not primary work. Qualification replicas, audit replicas, teacher search, schedule enumeration and invalid/incomplete callbacks add no primary matches. No architecture is selected in this ADR, and the current study must not be amended after its eight reference outcomes.

## Decision

Add new modules and an explicit `zone-rush-primary-continuation/2` protocol. Leave the legacy manifest, catalog, five stage trees, original bot, engines, worker and existing holdout modules unchanged. Do not label a v2 registration as v1 to bypass its checks.

A v2 continuation manifest will bind the original campaign/catalog hashes; the exact five-stage boundary; the observed terminal handoff; every legacy artifact and exported candidate; new evaluator/source/runtime pins; a conditional architecture-allocation rule; and the original two-million-match ceiling. Its own version ID is distinct from the original campaign ID. Both IDs are required in v2 receipts. This is a continuation of the existing slot budget, not another two-million-match campaign.

Each canonical credit slot is `(catalog_sha256, global_map_index, episode_0_to_199)`. Source changes, new task hashes, another directory or another protocol version cannot create another slot. An authenticated ledger enforces a unique key on this slot before and after admission. A repeated identical transfer is idempotent; a different row or provenance for an occupied slot fails closed.

### Preserve the legacy boundary

Before sealing an actual migration bridge, a reviewed read-only adapter must:

1. Bind `train_NNN` to the requested index, registration, summary and audit; require the precise catalog slices and all 200 episodes per map.
2. Validate actual rows and original proof coverage with the legacy validator, plus global task, rival-ID and rival-seed uniqueness. Recompute score summaries and check all artifact hashes against the already observed, pinned five-stage receipt set. A newly rehashed `approved` flag is insufficient.
3. Bind all raw registration/summary/audit files, sidecars, game logs, actor-audit logs, policy exports, catalog/manifest and source bytes in the new evaluator's authenticated bridge. Preserve old paths and bytes; references may identify them, not rewrite them.
4. State that the 100,000 matches were admitted under v1 with previously executed original audits. Do not call a transition hash scan a fresh 32-million-callback replay. Optional new legacy replay is zero-credit verification work.
5. Reject any unexpected prepared/played stage 5 or later, or any used heldout slot, until its provenance is reconciled. Do not infer an empty suffix merely from the latest completed stage.

The known terminal handoff is SHA `cfeae124ebe672eb9b5ceff3d567c7b4bebac5bcbcb2e73f12c2092d22869e61`. A new coordinator must acquire the SAME canonical campaign OS lease used by the existing guarded driver, confirm the previous owner is terminal, and reserve one authenticated canonical continuation output before packaging jobs. A stale PID file is not ownership. The original v1 executor does not itself acquire this newer lease, so it must remain retired; an OS lock cannot stop an unrelated program that ignores it.

### Architecture and evolution

Use the completed, fully admitted four-arm study and its preregistered analysis to make the architecture decision. No partial-result winner or new hand-picked arm is allowed. Record the study acceptance and selection-rule hashes in the migration. If the study is inconclusive, preserve multiple exact reference architectures as research controls instead of asserting a confirmed winner. The conditional allocation rule must be reviewed before consuming the next primary map.

Continue eight distinct candidates per training stage, with exact e8 incumbent control in slot 0. Carry a confirmed architecture anchor when one exists, multiple audited elites and bounded offspring; retain source-family diversity if the study is inconclusive. Specify the exact eight-slot recipe before execution. Every generation registers exports, parent IDs, family/template hashes, mutation kind, mutation RNG seed and gene values before its first primary match. Only admitted TRAIN outcomes can select future parents. No cross-generation raw-mean ranking, development feedback or final feedback may tune the population. Training fitness remains the equal mean of 64 seat/token/field cells, then raw score and source hash; it is unpaired research fitness, not a promotion confidence interval.

For e8-family candidates retain exact `GenomeSpace.export` validation. For Blocker/Feint, implement a separately reviewed source-family exporter: an exact original template plus explicitly whitelisted class-qualified numeric literal replacements, finite bounds and exact byte reconstruction. Defaults reproduce the original bytes. AST similarity or lack of `_history` alone must never admit arbitrary code. Preserve the final `act` constructor, direct `player.act` entry point, imports, inference/correctness logic, action legality and rules. The class's `__call__` has fallback behavior; switching the standalone entry point to it would be a policy change.

Initially keep `POOL`, `K1`, `K2`, `BAIT`, `DYN` and architecture-defining switches fixed. Candidate numeric groups can cover bounded economic weights and probability priors, with explicit class locations so `FeintBot.HOP_RISK` is not confused with `_Core.HOP_RISK`. Do not invent bounds after seeing development results. Exact-source legality/timing controls on already consumed training maps are zero-credit diagnostics, not fresh strength evidence. Any source-family expansion or search-budget mutation needs its own reviewed version and finite runtime controls. A fault stops the registered stage; there is no silent source replacement, STAY substitution or deletion of valid completed results.

The last scheduled training stage remains global stage 79. Its exact eight registered, distinct candidate exports, in registered order and including the incumbent, become the development shortlist. No manual substitution from the archive is permitted after stage 79.

### Schedule, fresh actors and seeds

Retain 200 episodes per map, all four focal seats and four starting tokens, map-major interleaving and the original four field-family multisets. Reproduce the old pair-occurrence candidate/field assignment: 2,500 matches per candidate in a 100-map training stage, each candidate/seat/token cell 156 or 157. Development carries occurrence offsets across its ten blocks; final uses one candidate. Keep hidden opponent parameters out of every actor's four-field public view.

New opponent IDs and seeds are reconstructed from the complete declared recipe, not merely checked for a plausible field label. A simple injective seed namespace is `2**64 + 4*(200*map_index + episode) + rival_seat`; every old v1 rival seed is a 64-bit value, so new rival seeds are provably disjoint from that prefix and mutually distinct. Verify actual reserved values anyway, including accepted other-version receipts. Python's current stdlib actors accept these integer seeds; any future backend needs its own qualification. Family shuffle, parameter sampling and mutation have separate domain-separated recipe seeds. Replaying/auditing a fixture intentionally uses its SAME seed and is not another primary game.

These seeds require explicit storage handling: SQLite INTEGER is signed 64-bit and JavaScript numbers cannot preserve their full integer precision. Keep the authoritative JSON/Python integer unchanged, use a fixed 9-byte unsigned big-endian BLOB for the global seed index, and never round-trip it through float/NumPy/int64 or a browser numeric parser. An alternative seed allocation would be another versioned recipe, not an incidental cast.

Create a fresh focal module/actor instance and fresh focal instance ID for every game. The exact reference Blocker/Feint entry point initializes its own RNG from the public seat. Do not secretly inject a per-game focal seed or call a different constructor while claiming the identical reference policy. The existing fresh-seed requirement applies to the three opponent instances; if randomized focal initialization is desired, register it as an explicit new architecture/source contract and requalify it. An unused metadata seed must not be presented as actual focal randomization.

### Remote execution and independent admission

Reuse the unchanged CPU worker and original `runner.play_game` / `oversight.audit_game(regenerate=True)` where their semantics fit. Reuse transport packaging only through normal supported roles and exact-source approvals; do not relabel shadow or extra-control results as primary.

Current runtime approvals cover the four exact reference focal sources; they do not qualify new structural mutants. The minimal safe first implementation qualifies each stage's eight exact exported SHAs on eight predeclared old-map diagnostic cases per helper. This avoids prematurely granting a broad structural-family runtime approval. Existing signed exact-source approval and frozen `build_shards` can then package them without changing the worker. The owner reference executions and helper replicas are zero-primary diagnostics. A later family-wide qualification shortcut needs independent review.

The v2 owner controller must implement this chain for every primary row:

1. Authenticated issued PLAY assignment, exact registration/source/runtime pins, original 80-turn row and authenticated creator identity.
2. Owner physical replay, legal/timing/input checks and canonical-slot reservation; no primary credit yet.
3. Owner-issued original-row audit assignment to a different declared physical helper, bound to creator evidence and exact original row SHA. Qualification replicas are not retagged as original-row audits.
4. Original full regeneration of all 320 actor decisions and both referees, signed by that auditor's registered credential. Source-specific legacy oracle count is derived from the actual four sources and may honestly be zero.
5. Owner reauthentication of the complete creator-to-auditor chain, all physical rows, exact coverage and source-specific counts, plus predeclared source/helper canaries. Only then seal 20,000 newly admitted primary slots.

Keep counters separate: full primary matches, helper qualification replicas, full actor audit callbacks, owner canary callbacks, legacy public-memory oracle checks and any teacher work. Original Blocker/Feint focal sources contribute zero legacy `_history` oracle checks; that does not reduce 320 actor-input/action checks or two-referee coverage. Do not manufacture an 80 count, assert a non-existent adapter, or compare an uncertain inferred belief to hidden truth as if it claimed exact knowledge. Additional architecture-specific inference checks may be versioned separately and truthfully counted.

An owner's NEW primary-evaluator HMAC authority seals migration, credit, population and heldout gates. It is separate from legacy heldout approval keys and the team transport registry. Existing helper keys may continue authenticating explicit work roles and runtime returns; no evaluator key enters a worker. Both authorities and purposes are bound in receipts. Authenticate before recovery/repair, rehash every bound raw artifact on resume, and fail closed on missing/replaced keys. Cooperative HMAC is not proof of computation, host integrity or physical independence. Claims must say REMOTE actor regeneration and OWNER physical replay/canaries, not owner regeneration of every callback.

Use the authenticated prefix cache to avoid repeating old physical replays at every stage: unchanged raw hashes plus a valid evaluator MAC retain prior admission; only new rows need new physical checks. A global uniqueness index is derived from actual admitted fixtures/rows, not a declared count. Bind its snapshot and raw source manifests, preserve prior signed states and append intent, and rebuild explicitly from authenticated evidence after corruption. Never silently sign a refreshed empty index. Measure hashing/index costs before a long continuation; a naive full physical-prefix replay at every generation creates quadratic work.

### Development and final admission

Add a v2 heldout adapter; do not pass mixed v1/v2 stages through `campaign_holdout/1`. Before the first development outcome, require the full 80-stage chain and exactly 1,600,000 disjoint admitted training slots. Validate the first five stages through their fixed bridge and the remaining stages through v2 actual evidence. Bind the exact last-eight shortlist, catalog, all raw training artifacts and source/runtime pins in a new authenticated gate. One deep admission followed by MAC verification plus full artifact rehashing preserves the existing cache trust model without replaying 1.6 million actors every resume. An unsigned refreshed hash manifest cannot bless missing proofs.

Development uses exactly the original 1,000 development maps and 200,000 matches. After all ten blocks are independently admitted, choose one policy using the existing exact-rational equal-cell metric, raw mean score tie-break and ascending source SHA. Seal that policy before creating any final task. Final uses exactly the 1,000 reserved final maps and 200,000 matches for this one policy. No mutation, reselection, extra finalist, replay credit or feedback tuning is allowed. Neither training nor heldout admission deploys a bot automatically. Fresh paired extra controls remain necessary for any stated promotion advantage.

## Existing incompatibilities and reuse boundaries

| Existing component | Concrete incompatibility | v2 treatment |
|---|---|---|
| `primary_campaign/core.py:load_catalog` | Couples catalog loading to exact current v1 source guards/incumbent | Preserve unchanged; independently bind catalog bytes and v1 identity in reviewed v2 loader |
| `prepare_generation` / `validate_registration` | Every focal must equal the e8 template's bounded CONFIG export; population builder knows one family | New v2 population/registration validator; no format alias or monkeypatch |
| `expected_opponents` | Derives v1 identities/seeds from v1 campaign context | New reconstructible seed/ID recipe and explicit version; same declared field distributions initially |
| `primary_campaign/run.py` | Re-prepares through v1 and rejects zero legacy oracle counts | New v2 coordinator/admission; reuse unchanged play/audit primitives, not v1 stage finalization |
| `campaign_monitor` / guarded driver | Understands homogeneous v1 stages, fixed interpreter and original root-path lease | Keep legacy verifier; v2 global union verifier takes the same canonical OS lease and explicit runtime provenance |
| `distributed_campaign/control.py` | Intentionally accepts only EXTRA four-arm study role and its own canonical binding | Reuse proven chain design, not its acceptance function or study reservation |
| `distributed_campaign/owner.py` | Primary prototype still ends in full owner audit and v1 validation | Not the new primary remote-admission implementation |
| `campaign_holdout/core.py` | Calls v1 validator for all 80 stages and insists every shortlist candidate is an e8 export | New mixed-version deep gate and source-family-aware exact shortlist exports |
| `campaign_holdout/run.py` | Delegates actor proofs to v1's 80–320 legacy-oracle validator | New source-specific validator with real zero allowed and all 320 callbacks mandatory |
| Existing heldout/team MACs | Different purposes, schemas and trust decisions | Keep intact; explicit new primary evaluator key/domain and authenticated bridges |

Current v1 guards require the root e8 source to remain unchanged. Before any eventual deployment changes that root file, preserve a reviewed runnable legacy source capsule or a separately reviewed content-addressed legacy reader. A path remap must resolve to the exact pinned bytes and must not waive original source hashes. This archival concern does not justify editing current guards or deploying during migration.

## Options and consequences

| Option | Benefit | Cost / flaw |
|---|---|---|
| Continue v1 for 75 stages | Lowest new code cost; existing acceptance works | Cannot evolve a stronger structural source; spends most remaining work inside one family |
| Edit v1 guards/templates/oracle thresholds in place | Superficially convenient | Invalidates source freezes, changes historical meaning and risks fake mixed-version approval; reject |
| Restart a fresh two-million-game catalog | Simple homogeneous schema | Discards valid work and violates the existing exact goal/holdout allocation; reject |
| Explicit v2 bridge and continuation | Preserves all valid work, supports bounded source families and real offload | Requires reviewed mixed-schema validator, new authority, admission and heldout adapter; proposed |

The proposal intentionally leaves algorithms and both referees on the actual CPU policy path. It makes no CUDA policy, speedup, universal optimality or completed-two-million-game claim. Source/runtime migration and broader opponent leagues remain explicit scientific changes, not hidden implementation details.
